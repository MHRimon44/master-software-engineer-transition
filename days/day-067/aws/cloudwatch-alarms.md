# Day 67 — CloudWatch Alarm Plan

## Objective

Detect API failures before users report them.

## 1. Primary Alarm: ALB 5xx Errors

Name:
team-task-prod-alb-5xx-high

Namespace:
AWS/ApplicationELB

Metric:
HTTPCode_Target_5XX_Count

Dimension:
TargetGroup + LoadBalancer

Statistic:
Sum

Period:
5 minutes

Threshold:
Greater than or equal to 5 errors

Evaluation:
2 out of 2 consecutive periods

Missing data:
Treat as missing

Notification:
SNS topic connected to the operations team

## 2. Expected Behavior

If target-generated 5xx errors reach
the threshold for two evaluation periods,
the alarm enters ALARM state.

An SNS notification can alert the team.

The threshold is an initial example,
not a universal production recommendation.

Tune it using real traffic and error rates.

## 3. Investigation Runbook

1. Confirm alarm timestamp.
2. Check ALB target health.
3. Inspect ECS service events.
4. Search CloudWatch application logs.
5. Group failures by requestId.
6. Check recent deployments.
7. Check RDS connectivity.
8. Identify the root cause.
9. Roll back if necessary.
10. Document the incident.

## 4. Additional Useful Alarms

- Unhealthy target count
- High API latency
- ECS CPU utilization
- ECS memory utilization
- RDS CPU utilization
- Low RDS free storage
- Database connection saturation

## 5. Important Distinction

HTTPCode_Target_5XX_Count:
5xx responses generated by targets.

HTTPCode_ELB_5XX_Count:
5xx responses generated by the load balancer.

Both may be worth monitoring.
